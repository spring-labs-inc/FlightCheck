name: develop-change
description: Run the repository's staged development workflow when the owner explicitly selects it for a bounded task or resumes that work.
---

Use the small first-flight guide when adopting the supplied evidence helpers. Capture the reviewer’s complete native final JSON through controller-owned capture; never replace it with an abridgment or give reviewers capture/write permissions. Start implementation from the prepared stage brief and applicable repository instructions. Confirm the project setup, scope, structured acceptance proof, checkout, and delivery boundary before editing. Declare native coverage baselines and a distinct retained test/fixture spec artifact before freezing; use the guide’s bootstrap/additive recipe for a new behavior. Export `handoff.py schema --kind challenge` or `review` for response types; use `challenge-review` to discuss ungrounded proposals before registration. Registered obligations still require the audited withdrawal process. Complete `handoff.py preflight` and the actual reviewer read-only boundary/access probes; keep the frozen acceptance contract across resumes. Consult the relevant section of the [project workflow](../../../workflow/docs/development-workflow.md) if the brief is missing or leaves an applicable rule or decision open.

Before selected-flight edits, run the delivered related-work detector and verify
native checkout selection through the shared Registry/configuration and
[checkout contract](../../../docs/checkout-verification.md). Record one actual main
checkout, explicit editing children, pinned base, authoritative default/protected
policy and observed client/session capabilities. Native choice accepts safe
branch-only or worktree execution; explicit worktree-required never silently
weakens. Isolated native detached work may remain detached until delivery needs a
branch. Retain `task.checkout_binding` for controlled checks/review and verify the
actual execution context on resume and delivery. Reconcile legitimate moves and
client handoffs explicitly without losing unfinished work or unrelated valid
proof. Release execution ownership with the #81 handoff inside PR & Merge; no
separate cleanup manager or universal command-interception claim.

At setup, consume the [lifecycle contract](../../../docs/flight-lifecycle.md):
record exact authorized flight-owned worktree/local-ref/actual-remote-ref inventory
and private/ignored preservation obligations separately from delivery. Historical
handoffs and names confer no cleanup authority. After confirmed merge, reconcile
actual integration and perform eligible disposition within PR & Merge before
closing. Prefer native cleanup, safely leave the execution path, retain a verified
external helper/card runtime and private history, and acknowledge actual removal.
Preserve active/locked/dirty/untracked/unknown-private, protected/shared/main and
unintegrated artifacts; report blockers rather than force a clean close. Interrupted
or repeated operations keep the same scope and old-OID conditions. The full
optional on-demand audit remains strictly read-only, including no fetch/prune;
report actionable recommendations and unavailable coverage without executing them.
This adds no outer review cycle or worktree/retention manager.

During Plan, give a separate read-only reviewer `handoff.py challenge-brief` before the implementation narrative. Retain its actual proposal with `handoff.py challenges`. Map each behavioral acceptance case and independent challenge to exact native witnesses and qualify its expected outcome using the guide's baseline or mutation controls. Include public observations, representation variants, and lifecycle timing where relevant to the project's contract. A green suite alone is insufficient.

Run the configured cheap checks, including fast checks for affected behavior, and resolve failures before interactive HTML approval or conditional early CODE review. Use the trusted recorder for gates assigned to the worker. At handoff, use `handoff.py checks` to carry verified receipts and identify the checks still due. Follow the guide for final code and evidence review and verdict routing. On resume, reconcile the current candidate, original results, owner decisions, and provider state before repeating work.

Record the early CODE decision and its reason for the current candidate using the brief's criteria or the [guide's criteria](../../../workflow/docs/development-workflow.md#decide-on-early-code-review). Reassess after material changes to scope, behavior, or evidence.

Use the guide's shared `handoff.py resume` summary before reopening saved evidence. Route an eligible clean resume directly to final review. For an applicable early CODE re-review, use `handoff.py code-review` to route an in-scope repair to the prior read-only reviewer. Build and validate the `handoff.py review` packet before launching the separate final reviewer. Resolve any blocked prerequisites and preserve the original outputs. Record actual reviewer JSON with `handoff.py requests`; execute requested checks as controller-owned gates after the request. For functional repairs, retain identical-test before-failure/after-pass evidence. Validate the actual final review with `handoff.py verdict` before authorized landing. See the guide for native review schema and explicit owner exceptions; never clear an obligation by omission.

For genuinely new flights, preflight freezes `review_protocol: "incremental-v1"`; use the guide's [bounded incremental evidence review](../../../workflow/docs/development-workflow.md#bounded-incremental-evidence-review) packet: current full and repair diffs, changed evidence, unresolved obligations, and acceptance claims mapped to effective dependency bindings and retained originals. No opt-in field is needed, and removing mutable `task.incremental` cannot downgrade that frozen protocol. Successful `verdict` retains the complete result in `task.review_validation`, from which later packets derive accepted proof automatically. Markerless existing contracts retain their legacy behavior and explicit incremental compatibility; records without bindings cannot establish automatic semantic reuse and need no archive reconstruction. Assess every final criterion and acceptance/challenge case, reusing valid accepted proof unless a concrete reason, changed dependency, contradiction or plausible specific counterexample warrants reopening it. Keep new defects discoverable without routine inspection of the entire historical archive.

Before incremental review, obtain the actual current reviewer read-only boundary/access report for the packet's manifest in the default private `reviewer-access.json`; access stays pending until the adapter actually probes the session. Optional `task.incremental` configures advanced report paths, explicit accepted-validation references, navigation and bounded `required_evidence` rather than activating fresh flights. Required evidence remains access-checked and digest-bound even for accepted claims. Controller filesystem reads cannot establish reviewer access. Necessary inaccessible evidence blocks review, but a covered inaccessible duplicate does not automatically do so. CODE leaves unrelated later gates pending. Bind native review to `decision_basis_sha256` and use `phase: "code"` for CODE; optional finding/request `dependency_ids` identify affected existing ledger obligations. Navigation-only changes preserve applicability only with unchanged candidate, decision content and verified target bytes plus fresh access validation. Candidate, diff, evidence, claim or obligation changes invalidate the prior basis or current verdict as applicable. Preserve conditional early CODE and one independent final skeptical code-and-evidence review, with no outer review cycle.

After every repair and restart, use `handoff.py next-action --target code` (or `final`) before review. Execute its run/reuse/reproduce/configure actions through the trusted controller and ask again. Send current failed checks directly to repair before review. Refresh affected proof at the existing gate granularity without narrowing fingerprints, and preserve unrelated valid proof and every outstanding obligation. Earlier APPROVE results with empty findings never erase retained obligations. Reconcile waiting attempts and damaged evidence; do not terminate a repair merely because its prior proofs became stale. A disputed oracle needs retained original-product counterevidence and explicit independent acknowledgment through the bounded disposition review, followed by full review.

For every selected flight in Codex, Claude or another supported client, follow the [controller status instructions](references/task-status.md). Start or restore the standard browser card on activation and resume. Before every user-facing controller reply, including progress, approval pauses, blockers, repairs and final handoff, prepare the current card and check the exact reply. Put the same task link last, with any recorded verdict above it. Proactively tell terminal/TUI users to open the live card in their regular browser. Ordinary chat and raw reviewer JSON stay outside this rule; reviewers never run controller lifecycle commands or hooks.

Use the shared `reply.py prepare` lifecycle for startup in every client; maintainer cards use that guard too. For SSH workers, obtain a browser-machine route through the supported client or installed `status-card/connect.py`. Never present worker-local HTTP success as browser reachability. Keep an unavailable status plain until startup and routing are established.
