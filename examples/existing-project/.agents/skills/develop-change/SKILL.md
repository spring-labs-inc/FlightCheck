---
name: develop-change
description: Run the repository's staged development workflow when the owner explicitly selects it for a bounded task or resumes that work.
---

Start implementation from the prepared stage brief and applicable repository instructions. Confirm the project setup, scope, structured acceptance proof, checkout, and delivery boundary before editing. Complete `handoff.py preflight` and the actual reviewer read-only boundary/access probes; keep the frozen acceptance contract across resumes. Consult the relevant section of the [project workflow](../../../docs/development-workflow.md) if the brief is missing or leaves an applicable rule or decision open.

During Plan, give a separate read-only reviewer `handoff.py challenge-brief` before the implementation narrative. Retain its actual proposal with `handoff.py challenges`. Map each behavioral acceptance case and independent challenge to exact native witnesses and qualify its expected outcome using the guide's baseline or mutation controls. Include public observations, representation variants, and lifecycle timing where relevant to the project's contract. A green suite alone is insufficient.

Run the configured cheap checks, including fast checks for affected behavior, and resolve failures before interactive HTML approval or conditional early CODE review. Use the trusted recorder for gates assigned to the worker. At handoff, use `handoff.py checks` to carry verified receipts and identify the checks still due. Follow the guide for final code and evidence review and verdict routing. On resume, reconcile the current candidate, original results, owner decisions, and provider state before repeating work.

Record the early CODE decision and its reason for the current candidate using the brief's criteria or the [guide's criteria](../../../docs/development-workflow.md#decide-on-early-code-review). Reassess after material changes to scope, behavior, or evidence.

Use the guide's shared `handoff.py resume` summary before reopening saved evidence. Route an eligible clean resume directly to final review. For an applicable early CODE re-review, use `handoff.py code-review` to route an in-scope repair to the prior read-only reviewer. Build and validate the `handoff.py review` packet before launching the separate final reviewer. Resolve any blocked prerequisites and preserve the original outputs. Record actual reviewer JSON with `handoff.py requests`; execute requested checks as controller-owned gates after the request. For functional repairs, retain identical-test before-failure/after-pass evidence. Validate the actual final review with `handoff.py verdict` before authorized landing. See the guide for native review schema and explicit owner exceptions; never clear an obligation by omission.

After every repair and restart, use `handoff.py next-action --target code` (or `final`) before review. Execute its run/reuse/reproduce/configure actions through the trusted controller and ask again. Earlier APPROVE results with empty findings never erase retained obligations. Reconcile waiting attempts and damaged evidence; do not terminate a repair merely because its prior proofs became stale. A disputed oracle needs retained original-product counterevidence and explicit independent acknowledgment through the bounded disposition review, followed by full review.

On activation or resume in interactive Codex with a configured status card, use the [chat status instructions](references/task-status.md). Put the status link first in the opening reply and last in the closing reply, with any recorded verdict directly below the closing link.
